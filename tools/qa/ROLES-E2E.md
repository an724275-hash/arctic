# Проверка ролевого маршрута

Запуск из корня проекта при работающих PostgreSQL, API на `127.0.0.1:8000`
и Vite на `127.0.0.1:5173`:

```powershell
node tools/qa/roles-e2e.cjs
```

Нужны Python окружение `backend/.venv`, Microsoft Edge и Playwright.
По умолчанию скрипт ищет Playwright в проекте и в установленном runtime Codex;
переменная `PLAYWRIGHT_MODULE` позволяет указать путь к установленному пакету.
Адрес фронтенда можно изменить через `E2E_BASE_URL`.

`create_roles_fixture.py` создаёт пять отдельных фиктивных аккаунтов и связь
наставника с участником. Фиктивному эксперту задаётся направление выбранной номинации. Пароль случайный, передаётся только через окружение
дочернего процесса и не попадает в отчёт. Существующие аккаунты и работы скрипт
не редактирует. Материалы явно помечены как QA, а ссылка на защиту ведёт на
`example.com`; перехода по ней и отправки писем нет.

Через браузер проверяются:

- вход каждой роли;
- закрытый II этап до теста и допуск после настоящей серверной проверки ответов;
  этот подготовительный шаг проходит через API на фиктивном аккаунте, не подменяет результат в базе;
- создание проекта и загрузка документа с презентацией;
- сохранение ID, полей и файлов черновика после перезагрузки;
- подача, возврат с комментарием, сохранение исправлений и повторная отправка;
- допуск организатором и назначение конкретного эксперта;
- авторизованный просмотр PDF;
- черновик рецензии, все критерии и предварительный взвешенный балл;
- сохранение рецензии сервером и запрет повторного редактирования в интерфейсе;
- скрытие неопубликованной оценки от участника;
- публикация результатов и назначение защиты;
- результат, комментарий и время защиты в кабинете участника;
- чтение результатов и рейтинга комиссией без управляющих форм;
- связанные участники, рецензия и защита в кабинете наставника;
- шесть экранов на ширинах 1440, 834 и 390 пикселей.

Дополнительно выполняется один отрицательный API запрос от комиссии:
публикация должна вернуть `403`. Действия успешного рабочего маршрута
выполняются через формы и кнопки интерфейса, а ответы API используются как
дополнительные подтверждения результата.

Артефакты: `frontend/test-results/roles-e2e/report.json`, PNG и accessibility
snapshot каждого проверенного экрана. Предыдущий отчёт сохраняется с ID запуска.
Тестовые записи остаются в локальной БД для последующей проверки. Это не
нагрузочный тест, не проверка VPS и не проверка внешней видеоконференции.

Запросы пяти браузерных сессий используют один локальный IP. Поэтому скрипт
отправляет их с интервалом не менее 1100 мс, сохраняя штатное ограничение API.
