# Arctic на Ubuntu 24.04 / 22.04: 1 vCPU / 2 ГБ / 30 ГБ

Практический комплект для одного VPS: nginx отдаёт собранный Vite frontend и проксирует `/api/` в FastAPI; PostgreSQL 17 и API не публикуют порты на хосте. Данные PostgreSQL, вложения и TLS-сертификаты находятся в именованных Docker volumes. Используется отдельный `deploy/compose.yaml`; не смешивайте его с корневым Compose для backend.

Фактические результаты серверного запуска и приёмки записываются в [status.json](status.json). Локальная подготовка конфигурации сама по себе не подтверждает сборку образов, выпуск сертификата или прохождение пользовательского сценария на VPS. Команды удаления чужих систем этот комплект автоматически не выполняет.

Локально проверены YAML, зависимости запуска, закрытые порты, адрес доверенного прокси, Python-синтаксис, LF у shell-файлов, генерация независимых секретов и отказ перезаписи `.env`. Docker и Bash в локальной Windows-среде недоступны; их реальные проверки выполняются на сервере и фиксируются отдельно.

## 1. Чистая система и файлы

Для текущего VPS выбрана Ubuntu 24.04. Установщик поддерживает также Ubuntu 22.04 и выбирает соответствующий репозиторий Docker: `noble` или `jammy`. Для дальнейших команд используются root и каталог `/opt/arctic`, в котором лежит корень проекта с `backend`, `frontend`, `deploy`. Перед переносом исключите `.env`, `.venv`, `node_modules`, `.runtime`, базы данных и `backend/storage`; секреты создаются заново на сервере.

```bash
cd /opt/arctic
bash deploy/install-docker.sh
python3 deploy/init-env.py http://95.85.251.67
bash deploy/up.sh
```

На этом VPS используется публичный IP `95.85.251.67`; домен не требуется для HTTPS: доступен [IP-сертификат Let's Encrypt](IP-TLS.md). HTTP нужен на первом этапе для проверки ACME. После запуска измените `PUBLIC_ORIGIN` и включите HTTPS по инструкции ниже. Домены `arctic.example.org` ниже служат только примерами и требуют замены. Генератор не перезаписывает существующую `.env`, не выводит секреты и не создаёт демонстрационных пользователей.

Для сборки на 2 ГБ памяти используется последовательная сборка и лимит Node heap 512 МБ. Если сервер без swap, до сборки можно создать 2 ГБ swap **только при отсутствии `/swapfile`**:

```bash
test -e /swapfile || { fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile; }
grep -q '^/swapfile ' /etc/fstab || printf '/swapfile none swap sw 0 0\n' >> /etc/fstab
```

Публикуются только 80 и 443; SSH-порт остаётся настроенным системой. Firewall провайдера должен разрешать HTTP/HTTPS. Docker-публикация может обходить правила UFW, поэтому база и API вообще не имеют `ports`. Сеть `172.30.82.0/24` не должна пересекаться с существующей сетью/VPN. При смене подсети синхронно измените IP nginx и `FORWARDED_ALLOW_IPS`.

## 2. HTTPS

Для текущего IP измените `PUBLIC_ORIGIN` в `deploy/.env` на `https://95.85.251.67` и запустите `bash deploy/enable-ip-tls.sh 95.85.251.67` из корня проекта. Скрипт установит IP-сертификат и systemd timer продления дважды в сутки. [Требования, проверка SAN, dry-run и эксплуатационные границы](IP-TLS.md).

Следующий вариант предназначен только для домена:

DNS A домена должен указывать на этот VPS. Если есть AAAA, она тоже должна вести на рабочий адрес этого сервера либо быть удалена администратором DNS. Порт 80 нужен для ACME-проверки и продления. Облачный прокси перед nginx в этой конфигурации не используется.

```bash
cd /opt/arctic
bash deploy/enable-tls.sh arctic.example.org admin@example.org
```

Перед запуском в `deploy/.env` должен стоять `PUBLIC_ORIGIN=https://arctic.example.org`. Скрипт получает сертификат через webroot, проверяет конфигурацию nginx, ожидает готовности API с обновлённым origin, затем включает 443 и перенаправление с HTTP; при ошибке `nginx -t` восстанавливает прежний конфиг. Приватный ключ остаётся в volume сертификатов.

Для доменного варианта поставьте продление дважды в день системным cron после успешного первого выпуска. Если уже используется `arctic-cert-renew.timer` из IP-сценария, оставьте его: он продлевает все сертификаты этого Compose, дополнительный cron не нужен.

```bash
printf '17 3,15 * * * root /bin/bash /opt/arctic/deploy/renew-tls.sh >> /var/log/arctic-cert-renew.log 2>&1\n' > /etc/cron.d/arctic-cert-renew
chmod 644 /etc/cron.d/arctic-cert-renew
```

## 3. Каталог и администратор

```bash
cd /opt/arctic/deploy
docker compose exec api python -m app.seed --admin-email admin@example.org
```

Введите новый пароль в скрытом запросе. Seed создаёт администратора и начальный каталог; тексты/вопросы каталога демонстрационные и требуют замены организатором. Для отдельного демонстрационного стенда можно запустить `docker compose exec api python -m app.seed --demo` и задать отдельный пароль; автоматически это не делается.

## 4. Важные переменные

| Переменная в `deploy/.env` | Значение |
| --- | --- |
| `PUBLIC_ORIGIN` | Единственный публичный origin сайта, без `/api`, пути и завершающего слеша. Идёт в ссылки почты, QR и CORS |
| `POSTGRES_PASSWORD` | Генерируется при первом запуске. Не менять поверх существующего PostgreSQL volume без изменения пароля внутри БД |
| `JWT_SECRET` | Отдельный случайный секрет; смена делает существующие JWT недействительными |
| `ENABLE_EMAIL_DELIVERY` | По умолчанию `false`; регистрация/восстановление сохраняют задания в outbox |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` | Настоящий SMTP-провайдер. Порт 587 и STARTTLS включены по умолчанию |
| `SMTP_STARTTLS` | `true` для STARTTLS. Код не реализует implicit SMTP SSL на 465 |

Frontend всегда использует `/api/v1` на том же origin. Nginx перезаписывает `X-Forwarded-For` адресом прямого клиента, а API доверяет только IP nginx `172.30.82.10`. Значение `*` не требуется. Для CDN/внешнего load balancer нужна отдельная проверенная настройка реального IP.

Для отправки писем после настройки `.env`:

```bash
docker compose --profile mail up -d --wait api mail-worker
docker compose logs --tail=40 mail-worker
```

Не публикуйте вывод `docker compose config`: он разворачивает секреты. В скрипте используется только `config --quiet`. Swagger снаружи закрыт nginx, серверные healthcheck остаются рабочими. Загрузка файлов ограничена API до 30 МБ, nginx допускает 32 МБ с учётом multipart.

## 5. Приёмка после развёртывания

```bash
cd /opt/arctic/deploy
docker compose ps
docker compose exec -T web nginx -t
curl --fail https://arctic.example.org/health/ready
curl --fail https://arctic.example.org/api/v1/quiz/config
docker compose exec -T api python -m alembic current
docker compose logs --tail=60 api
```

На публичном HTTPS-адресе вручную пройти регистрацию, вход, тест, перезагрузку с сохранением ответа, получение PDF, создание и подачу проекта с файлом. Проверить download вложения и PDF/QR по публичному URL, ролевые кабинеты, выход. Проверить восстановление пароля только после включения SMTP. Логи не должны содержать токены и тела писем.

## 6. Обновление и резервная копия

Обновлять исходники, сохраняя `deploy/.env` и `deploy/.runtime`, затем запускать `bash deploy/up.sh` из корня проекта. Миграции выполняются до нового API. Nginx использует Docker DNS с TTL 10 секунд, поэтому перезапуск API не оставляет старый IP upstream. Один worker выбран намеренно: лимиты запросов API хранятся в памяти процесса.

Перед миграциями сохраняйте БД **и** вложения. Два скрипта ниже запускаются от root. На время копирования API и фактически запущенный `mail-worker` останавливаются, поэтому сайт кратковременно не сможет выполнять запросы. Не запускайте параллельно миграции, другие экземпляры приложения или ручную запись в БД/uploads. Уже работающая миграция блокирует копирование; общий `flock` исключает наложение backup и его проверки.

```bash
cd /opt/arctic
bash -n deploy/backup.sh deploy/verify-backup.sh
bash deploy/backup.sh
# Подставьте точный каталог из строки Backup created предыдущей команды.
bash deploy/verify-backup.sh '/var/backups/arctic/<UTC-directory>'
```

Последнюю строку выполняйте после замены `<UTC-directory>` на реальное имя. `backup.sh` создаёт уникальный `/var/backups/arctic/<UTC>.<suffix>` с правами `700`; файлы имеют права `600`. Внутри: `database.dump` (PostgreSQL custom), `uploads.tar.gz`, `deployment.env`, имена всех таблиц `public` и числа строк, SHA-256 и метаданные. Секреты не печатаются. Запущенные до копирования API/worker возвращаются через `trap`, включая обычные ошибки и SIGINT/SIGTERM; выключенный worker не включается. При SIGKILL, аварии Docker или отключении питания shell не может выполнить trap — проверьте состояние сервисов вручную. Частичные копии сохраняются с `INCOMPLETE`, старые копии не удаляются. Если возвращение сервиса не удалось, скрипт завершится с ошибкой и укажет закрытый журнал `services.log`.

`verify-backup.sh` проверяет SHA-256 всех пяти известных файлов, целостность gzip/tar и структуру dump. Затем создаёт уникальную БД `arctic_verify_<timestamp>_<pid>_<random>`, восстанавливает туда dump одной транзакцией и сравнивает имена, количество таблиц и **число строк каждой таблицы** с сохранённой копией, включая пользователей, проекты, попытки теста и outbox. Production-база не является целью восстановления: `pg_restore --create/--clean` не используются. Временная БД удаляется после успеха или ошибки через trap, только если именно этот запуск успешно создал её. Проверка не извлекает архив uploads поверх рабочих файлов и не отправляет письма. Отчёт остаётся внутри backup в `verify-<UTC>.<suffix>/status.txt`; успешный отчёт содержит `passed`. Для проверки требуется свободное место под вторую БД. Обычные ошибки restore пишутся в закрытый `database.log`, поскольку PostgreSQL может включить данные строки в диагностику.

Эта процедура подтверждает восстановимость dump и читаемость архива, но не заменяет полный пользовательский сценарий после аварийного восстановления. Переносите проверенную копию за пределы VPS в защищённое хранилище: она содержит личные данные и секреты `.env`. Восстанавливайте только собственные доверенные dump — SQL из backup выполняется сервером PostgreSQL. Системные настройки, исходники и TLS-сертификаты в этот архив не входят; код хранится отдельно, сертификаты можно выпустить заново. Права файлов, индексы и ограничения создаются `pg_restore`, сравнение строк не доказывает побайтовое совпадение отдельных полей. Скрипты не удаляют старые backups и не выполняют восстановление поверх production. `docker compose down` сохраняет volumes; `down -v` уничтожает данные этого проекта.

На текущем VPS проверка выполнена: [обезличенный receipt](../docs/deployment/vps-receipt.json) фиксирует `passed`, 22 таблицы и завершение 13.10.2026 13:08:40 UTC. Исходный закрытый `status.txt` остаётся на сервере внутри backup; данные копии в командный ZIP не включены. Порядок восстановления опирается на документацию [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html) и [dropdb](https://www.postgresql.org/docs/17/app-dropdb.html).

Лимиты контейнеров: PostgreSQL 600 МБ, API 700 МБ, nginx 96 МБ, необязательный worker 192 МБ. Они оставляют место ОС, но не доказывают выдерживание 10 000 участников. На 30 ГБ контролируйте uploads, Docker images и резервные копии. Логи ограничены 3 файлами по 10 МБ на контейнер.

Официальные справочники, проверенные при подготовке: [Docker на Ubuntu](https://docs.docker.com/engine/install/ubuntu/), [порядок запуска Compose](https://docs.docker.com/compose/how-tos/startup-order/), [nginx proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).
